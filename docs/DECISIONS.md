## D-004 공통 뼈대·첫 화면 담당

- **결정:** 공통 파일(라우터 등록, 화면 레이아웃, DB 설정)은 건용이, 첫 화면(Home)은 은희가 맡는다.
- **배경:** 두 역할의 담당이 "미정"이라 공통 뼈대 작업을 시작할 사람이 없었다.
- **이유:** 한 명씩 추첨으로 정했다. (AI가 임의로 고른 결과이며, 추첨 프로그램은 쓰지 않았다.)
- **다른 선택지:** 여행기록 담당(서준)이 공통 뼈대와 Home을 함께 맡는 안
- **누가·근거:** 사람이 추첨 결과를 승인함
- **영향:** 건용은 여행 다이어리와 공통 뼈대를, 은희는 여행지 정보와 Home을 함께 맡는다.
- **다시 볼 조건:** 한 사람에게 작업이 몰려 일정이 밀릴 때
- **상태:** 유효

## D-005 설계 문서의 공통·개별 구분

- **결정:**
  - 공통 문서: `PRD`, `ARCHITECTURE`, `DATA-MODEL`, `API-SPEC`
  - 개별 문서: `SCREEN-SPEC`, `TEST-PLAN` (`TEST-PLAN`에는 기능 사이 연결·회귀 검사를 다루는 공통 절을 하나 둔다)
  - 모든 문서는 `docs/` 아래 한 파일로 두고, 기능별 내용은 그 파일 안의 담당자별 절에 쓴다.
  - 절 담당: 여행기록·`trips`는 서준, 여행지 정보·`places`·Home은 은희, 여행 다이어리·`diaries`·공통 레이아웃은 건용. `ARCHITECTURE` 초안은 공통 뼈대 담당인 건용이 쓴다.
- **배경:** 기능 3개를 담당자 3명이 나눠 맡아, 문서마다 누가 무엇을 쓰는지 정해야 했다.
- **이유:** 한 사람이 바꾸면 다른 기능이 깨질 수 있는 문서(테이블 연결 `trip_id`, Home이 쓰는 목록 API 등)는 공통으로 둔다. 자기 기능 안에서 끝나는 문서는 개별로 둔다. 기능별 파일로 나누지 않으면 `AGENTS.md`의 문서 목록을 바꾸지 않아도 된다.
- **다른 선택지:** 개별 문서를 기능별 파일로 나누는 안 (예: `docs/screen-spec/trips.md`). Git 충돌은 줄지만 `AGENTS.md`·`README.md`의 문서 목록을 고쳐야 한다.
- **누가·근거:** 사람이 AI의 제안 중 "한 파일 안에 담당자별 절" 안을 승인함
- **영향:** 같은 파일을 여러 명이 고치므로 Git 충돌이 날 수 있다. 공통 문서를 고칠 때는 팀에 먼저 알린다.
- **다시 볼 조건:** 같은 문서에서 Git 충돌이 자주 날 때
- **상태:** 대체됨 (D-007)
- **날짜:** 2026-10-19

## D-007 설계 문서의 공통·개별 구분과 고치는 규칙

- **결정:**
  - 공통 설계 문서: `PRD`, `ARCHITECTURE`, `DATA-MODEL`, `API-SPEC`
  - 개별 문서: `SCREEN-SPEC`, `TEST-PLAN` (`TEST-PLAN`에는 기능 사이 연결·회귀 검사를 다루는 공통 절을 하나 둔다)
  - 모든 문서는 `docs/` 아래 한 파일로 두고, 기능별 내용은 그 파일 안의 담당자별 절에 쓴다.
  - 절 담당: 여행기록·`trips`는 서준, 여행지 정보·`places`·Home은 은희, 여행 다이어리·`diaries`·공통 레이아웃은 건용. `ARCHITECTURE` 초안은 공통 뼈대 담당인 건용이 쓴다.
  - 공통 설계 문서는 공통 문서(README, AGENTS, DECISIONS 등)와 같이 팀이 합의한 뒤에만 고친다. 담당자별 절도 마찬가지다.

- **이유:** 한 사람이 바꾸면 다른 기능이 깨질 수 있는 문서이므로, 다른 공통 문서와 같은 규칙으로 맞춘다.

- **다시 볼 조건:** 같은 문서에서 Git 충돌이 자주 나거나, 합의를 기다리느라 일정이 밀릴 때

## D-008 빌드 도구와 스타일 방식

- **배경:** README와 PLAN에 "제안 (미정)"으로 남아 있어 ARCHITECTURE를 쓸 수 없었다.

## D-015 장소·일기가 붙은 여행 지우기

- **결정:**
  - 장소나 일기가 하나라도 붙은 여행은 지울 수 없다.
  - DB: `places.trip_id`, `diaries.trip_id`를 `REFERENCES trips(id) ON DELETE RESTRICT`로 두고, `backend/database.py`가 연결할 때마다 `PRAGMA foreign_keys = ON`을 켠다.
  - `trips` 라우터: 지우기 전에 그 여행의 장소·일기 개수를 세고, 하나라도 있으면 지우지 않는다.

- **이유:** 다른 사람 기능의 데이터가 여행과 함께 사라지는 일을 막는다. DB가 막으면 라우터를 거치지 않는 길로도 지워지지 않고, 라우터가 개수를 세면 화면 안내 문구에 개수를 쓸 수 있다 (SCREEN-SPEC 3절 4번).
- **다른 선택지:** 연결된 장소·일기를 함께 지우는 안(`ON DELETE CASCADE`). DB 외래 키만 쓰는 안. 라우터 검사만 쓰는 안.
- **누가·근거:** 사람이 AI의 제안 중 고르고, 팀 합의로 보고 진행하라고 승인함

## D-016 DB 저장 규칙

- **결정:**
  - DB 필드 이름은 영어 snake_case로 쓴다 (`trip_id`, `start_date`). 코드의 이름 규칙은 여전히 미정이다.

## D-017 만든·고친 시각

- **결정:**
  - 모든 테이블에 `created_at`, `updated_at`을 둔다. 형식은 `TEXT`, `YYYY-MM-DD HH:MM:SS`, 한국 시각이다.
  - 처음에는 DB 기본값 `datetime('now', 'localtime')`이 넣고, 고칠 때는 그 테이블의 라우터가 `updated_at`을 넣는다. 트리거는 쓰지 않는다.
  - 기록용이며, 날짜(또는 날짜·시각)가 같을 때의 순서는 그대로 `id`로 가른다.
  - API 응답에 넣을지는 `docs/API-SPEC.md`에서 정한다.
- **배경:** PRD 공통 #2는 "만든 시각은 따로 저장하지 않는다"였다. 사람이 모든 테이블에 두 컬럼을 넣기로 했다.
- **이유:** 같은 초에 만든 줄은 `created_at`으로 순서를 가를 수 없어 `id`가 필요하다. `id`를 유지하면 PRD의 순서 규칙(L-11, H-05, R-D-008)을 바꾸지 않아도 된다. `CURRENT_TIMESTAMP`는 UTC로 들어가 한국 시각과 다르다.
- **다른 선택지:** 만든 시각을 저장하지 않는 안 (PRD 공통 #2 처음 안). 순서를 `created_at`으로 가르는 안. `updated_at`을 트리거로 바꾸는 안.
- **누가·근거:** 사람이 두 컬럼을 넣기로 정하고, 세부 방식은 AI의 제안대로 팀 합의로 보고 진행하라고 승인함
- **영향:** 세 라우터가 고칠 때마다 `updated_at`을 넣어야 한다. `docs/DATA-MODEL.md` 1~4절, `docs/PRD.md` 공통 #2·H-05, `docs/TEST-PLAN.md`(P-09)
- **다시 볼 조건:** 만든·고친 시각을 화면에 보여 주려 할 때
- **상태:** 유효
- **날짜:** 2026-10-21

## D-019 서버 검사와 오류 응답

- **결정:**
  - 서버도 화면과 같은 입력 규칙(필수, 글자 수, 날짜 형식, 기간 안, 시·도 17개, 기분 5개, 시각 형식)을 검사한다.
  - 오류 응답은 FastAPI 기본 모양 `{"detail": ...}`을 그대로 쓴다.
  - 상태 코드: 입력 규칙 위반 422, 주소의 `{id}`가 없음 404, 장소·일기 때문에 막힘 409.
  - 409에는 `detail` 안에 `place_count`, `diary_count`를 넣는다. 여행 지우기는 붙은 개수, 기간 수정은 새 기간 밖 개수다.
  - 여행 상세에서 "삭제"를 누를 때의 안내는 화면이 이미 불러온 장소·일기 목록의 개수로 먼저 보여 준다.
- **배경:** DATA-MODEL 2~4절과 SCREEN-SPEC 3·4절이 서버 검사 여부, 오류 응답 모양, 지우기·기간 수정을 막을 때의 개수를 `API-SPEC`으로 넘겼다.
- **이유:** 화면을 거치지 않는 요청도 DB에 잘못된 값이 들어가지 않게 막는다 (D-015와 같은 생각). 기본 모양을 그대로 쓰면 공통 파일 `backend/main.py`에 오류 처리기를 따로 넣지 않아도 된다. 개수를 409에 넣으면 개수만 세는 API를 따로 만들지 않아도 된다.

## D-027 변수·함수 이름과 서버 호출 모양

- **결정:**
  - 프론트엔드(JavaScript)의 변수·함수 이름은 camelCase로 짓는다.
  - 백엔드(Python)의 변수·함수 이름은 snake_case로 짓는다 (PEP 8, DB 필드 이름 D-016과 같다). 라우터 함수는 `list_trips`, `get_trip`, `create_trip`, `update_trip`, `delete_trip` 모양으로 짓는다 (장소·일기도 같다).
  - `frontend/src/api/` 함수 이름은 "동사 + 대상"으로 짓는다.
    - 지금 있는 것: `getTrips()`, `getPlaces(tripId)`, `getDiaries(tripId)`
    - 앞으로 만들 것: `getTrip(id)`, `createTrip(data)`, `updateTrip(id, data)`, `deleteTrip(id)` 같은 모양 (장소·일기도 같다)
  - `api/` 함수는 성공하면 응답 JSON을 돌려준다 (`204`이면 `null`). 실패하면 `Error`를 던지고, 그 `Error`에 `status`(422·404·409 등)와 `detail`(서버의 `detail`, 없으면 `null`)을 담는다. 화면은 `try`/`catch`로 받는다.
  - 서버에 닿지 못하면 `fetch`가 던지는 오류를 그대로 둔다 (`status` 없음).
  - 오류를 던지는 공통 부르기 함수(`request`)는 `trips.js` · `places.js` · `diaries.js`에 각각 둔다. 공통 파일을 따로 만들지 않는다.
- **배경:** P-14(화면·서버 연결)에서 `api/` 함수를 처음 만들었다. 변수·함수 이름 규칙이 미정이었고(AGENTS 공통 규칙), 화면이 오류를 받는 모양도 정하지 않았다.
- **이유:** camelCase는 JavaScript와 React에서 흔히 쓰는 방식이다. snake_case는 Python 표준 방식이고, 이미 만든 라우터 함수(`list_trips` 등)와 같다. `Error`에 `status`와 `detail`을 담으면 화면이 409의 개수(`place_count`, `diary_count`)로 안내를 만들 수 있고, 422는 공통 저장 실패 문구로 보일 수 있다 (D-019, D-021). 공통 코드를 세 파일에 두면 정한 폴더 구조(D-010)와 "기능별 파일 하나씩"(AGENTS 코드 규칙)을 바꾸지 않는다.
- **다른 선택지:** `fetch` 앞붙임(`fetchTrips`). 실패해도 던지지 않고 `{ ok, status, data }`를 돌려주는 안. 공통 코드를 `api/request.js` 한 곳에 두는 안. 백엔드 이름 규칙은 미정으로 두는 안.
- **누가·근거:** 팀이 함께 P-14를 하며 AI 제안대로 정함 (PLAN P-14)
- **영향:**
  - `request`를 고치면 세 파일을 같이 고쳐야 한다.
  - `AGENTS.md` 공통 규칙의 "이름 규칙: 미정", `docs/ARCHITECTURE.md` 3절, `docs/API-SPEC.md` 1절 "주고받는 값", `docs/PLAN.md` "남은 문제"의 이름 규칙 줄
  - 이름 규칙에서 남은 것은 CSS Module 클래스 이름과 브랜치 이름이다.
- **다시 볼 조건:** `request`를 세 파일에서 따로 고치다 서로 달라질 때, 화면에서 서버에 닿지 못한 오류를 따로 다뤄야 할 때
- **상태:** 유효

## D-029 글자 값의 앞뒤 공백과 `PUT` 검사 순서

- **결정:**
  - 필수 글자 값(여행명·여행지, 장소 이름, 일기 제목)은 서버가 앞뒤 공백을 빼고 저장한다. 글자 수(20자·50자)도 뺀 뒤 센다. 빼고 나서 비면 `422`다 (D-021).
  - 선택 글자 값(여행 정보, 장소 메모, 일기 본문)은 앞뒤 공백을 빼고 저장한다. 비우거나 공백만 적으면 `null`로 저장한다.
  - 날짜는 `YYYY-MM-DD` 꼴이고 실제로 있는 날짜만 받는다. `20260101`처럼 꼴이 다르면 `422`다.
  - `PUT`의 검사 순서는 본문 규칙 `422` → 없는 `id` `404` → 장소·일기 때문에 막힘 `409`(여행만)다. FastAPI가 본문을 라우터보다 먼저 검사하는 순서를 그대로 쓴다. `DELETE`는 `404` → `409`(여행만)다.
  - 이것으로 API-SPEC 1절 열린 질문 A-02를 닫는다.
- **배경:**
  - P-23(여행기록 API)을 만들며 정해야 했다. D-021은 "공백만이면 422"만 정했고, 저장할 때 공백을 빼는지는 정하지 않았다.
  - A-02는 API-SPEC의 `404 → 422 → 409`(AI 제안)가 FastAPI에서 지켜지는지 묻는 열린 질문이었다.
- **이유:**
  - 공백을 빼고 저장하면 목록·select·Home 카드에 빈칸이 생기지 않고, 글자 수도 보이는 만큼만 센다.
  - FastAPI 기본 순서를 쓰면 세 라우터의 코드가 간단하고 서로 같아진다.
  - TEST-PLAN은 순서를 검사하지 않는다 (TEST-PLAN 3절 6번). 없는 `id`에 틀린 본문을 보내는 일은 화면에서는 생기지 않는다.
- **다른 선택지:**
  - 공백만인지 검사하고, 적은 값은 그대로 저장하는 안
  - `404 → 422 → 409`를 지키려고 본문을 라우터에서 직접 검사하는 안
  - A-02를 열어 두는 안
  - 공백 규칙을 여행기록에만 적용하는 안
- **누가·근거:** 팀이 함께 P-23을 하며 AI 제안대로 정함 (PLAN P-23)
- **영향:**
  - `backend/routers/trips.py`(P-23)에 적용했다. `places.py`(P-26)와 `diaries.py`(P-30)도 같은 규칙으로 만든다.
  - `docs/API-SPEC.md` 1절 열린 질문 A-02, 2~4절 "3. 요청 본문과 서버 검사" 표, "4. API별 규칙"의 `PUT` 검사 순서 줄
  - `docs/PLAN.md` "남은 문제"의 `PUT` 검사 순서 줄
- **다시 볼 조건:** 화면이 `422`를 받아 칸별 안내를 보여야 할 때 (D-019·D-021과 같음), 없는 `id`에 `404`를 먼저 보여야 할 화면이 생길 때
- **상태:** 유효

## D-033 여행·장소·일기 사진

- **결정:**
  - README "만들지 않는 것"의 "사진 업로드"에 예외를 둔다. 여행 대표사진 0~1장, 장소 사진 0~4장, 일기 사진 0~1장만 만든다. 그 밖의 사진 업로드는 여전히 만들지 않는다.
  - 사진 파일은 DB에 넣지 않고 `backend/uploads/`에 둔다. DB에는 서버가 붙인 파일 이름(uuid 32자 + 확장자)만 넣는다. `backend/uploads/`는 Git에 올리지 않는다.
  - 사진은 공통 업로드 API `POST /api/uploads`(`multipart/form-data`)로 먼저 올려 파일 이름을 받고, 여행·장소·일기를 저장할 때 JSON 본문에 그 이름을 넣는다. 보기는 `GET /api/uploads/{filename}`이다. `/api`로 시작하므로 Vite 프록시 설정은 바꾸지 않는다 (D-011).
  - 올리기 라우터는 `backend/routers/uploads.py`로 따로 두고 건용이 관리한다(공통 파일). 파일 받기에 필요한 `python-multipart`를 설치해 `requirements.txt`에 버전을 고정한다 (D-026).
  - DB: `trips.photo`, `diaries.photo`(`TEXT`, 비울 수 있음)를 더하고, 장소 사진은 새 테이블 `place_photos(place_id, filename …)`에 한 장씩 둔다 (은희 담당).
  - 형식은 jpg·jpeg·png·webp, 한 장 5MB 이하다. 화면과 서버가 함께 검사한다 (D-019).
  - 사진을 바꾸거나 빼서 저장하거나 기록을 지우면 전 사진 파일도 라우터가 지운다.
  - 테이블 모양이 바뀌므로 팀원 각자 `backend/yeoback.db`를 지우고 다시 만든다. 넣어 둔 데이터는 사라진다.
  - 여행기록 카드에서 사진이 없을 때는 지금 조각보 무늬를 그대로 쓴다. Home 카드에는 사진을 보이지 않는다.
  - 사진 기능 작업(P-35~P-39)은 담당자를 나누지 않고 팀이 함께 한다.
- **배경:** 팀이 여행기록·장소·일기에 사진을 넣기로 합의했다 (2026-10-22). README·PRD는 "사진 업로드"를 만들지 않는 것으로 두었고, PRD R-D-017(일기 사진)도 그 이유로 제외였다.
- **이유:**
  - 파일로 두면 DB가 커지지 않고 목록 응답이 가볍다.
  - 공통 업로드 API를 쓰면 여행·장소·일기의 저장 API는 지금처럼 JSON을 그대로 쓰고 사진 칸만 더하면 된다. 세 기능이 같은 방법을 쓴다.
  - 장소 사진은 여러 장이라 칸 하나에 목록을 글자로 넣기보다 한 줄에 한 장씩 두는 편이 DB에서 검사하고 지우기 쉽다.
  - 파일 이름을 서버가 새로 붙이면 한글 이름·같은 이름·경로 문자(`../`) 문제가 생기지 않는다.
  - 기존 DB를 고치는 코드(`ALTER TABLE`)를 두지 않고 다시 만드는 편이 간단하다. 아직 실제 사용자 데이터가 없다.
- **다른 선택지:**
  - 사진을 DB에 Base64 글자로 넣는 안 (새 패키지가 필요 없지만 DB와 목록 응답이 무거워짐)
  - 여행·장소·일기의 `POST`·`PUT`이 사진과 글자를 한 번에 `multipart`로 받는 안 (연결되지 않은 파일은 안 생기지만 세 API의 요청 모양이 모두 바뀜)
  - 장소 사진을 `places`의 칸 하나에 JSON 목록으로 넣는 안
  - `init_db`에서 칸이 없으면 `ALTER TABLE`로 더하는 안 (데이터는 남지만 코드가 늘어남)
  - 사진이 없는 여행에 다른 빈 그림을 보이는 안
- **누가·근거:** 팀이 범위(여행 0~1, 장소 0~4, 일기 0~1)와 파일 저장·DB 다시 만들기·조각보 유지를 정함. 업로드 방식·`place_photos`·형식·용량·이름 규칙은 AI 제안 중 사람이 골라 정함 (2026-10-22, PLAN P-35)
- **영향:**
  - `README.md` 주요 기능·만들지 않는 것·기술 스택·폴더 구조, `docs/PRD.md` 1~4절(R-T-020, R-P-022, R-D-017), `docs/DATA-MODEL.md` 1~5절, `docs/API-SPEC.md` 1~5절, `docs/ARCHITECTURE.md` 1~5절, `docs/SCREEN-SPEC.md` 1·3·4·5절, `docs/DESIGN.md` 6~8·11절, `docs/TEST-PLAN.md`, `docs/PLAN.md` P-35~P-39
  - 코드: `backend/database.py`·`main.py`·`requirements.txt`·`routers/uploads.py`(새 파일), 세 라우터와 `frontend/src/api/` 세 파일, 여행·장소·일기의 폼과 표시 화면, `.gitignore`
  - 여행 상세의 장소·일기 목록(P-34)은 장소 카드·일기 목록을 가져다 쓰므로 사진이 함께 보인다.
  - 올리기만 하고 저장하지 않은 사진 파일은 지우지 않고 남는다 (PLAN "남은 문제").
- **다시 볼 조건:** 연결되지 않은 사진 파일이 많이 쌓일 때, 사진을 더 여러 장 넣자는 의견이 나올 때, 실제 데이터가 생겨 DB를 다시 만들 수 없을 때, 사진 때문에 화면이 느릴 때
- **상태:** 유효
- **날짜:** 2026-10-22

## D-034 화면 제목을 메뉴 이름에 맞추기

- **결정:** 목록 화면 제목을 "여행 + 메뉴 이름" 꼴로 바꾼다. 메뉴 "여행" → `/trip` 제목 "여행 기록", 메뉴 "장소" → `/place` 제목 "여행 장소", 메뉴 "일기" → `/diary` 제목 "여행 일기". 메뉴 이름(D-032)과 화면 주소(D-012)는 그대로다. 기능 이름(D-001~D-003의 "여행기록"·"여행지 정보"·"여행 다이어리")과 문서의 절 이름은 바꾸지 않는다.
- **배경:** D-032로 메뉴는 "여행 · 장소 · 일기"인데 화면 제목은 "여행기록 · 여행지 정보 · 여행 다이어리"라, 메뉴를 눌러 들어간 화면의 제목이 메뉴와 이어지지 않았다.
- **이유:** 제목에 메뉴 이름이 그대로 들어 있어 지금 어느 화면인지 바로 알 수 있다. 메뉴는 짧게 두어 좁은 화면(360px)에서도 한 줄에 들어간다.
- **다른 선택지:** 메뉴도 "여행 기록 · 여행 장소 · 여행 일기"로 바꿔 제목과 똑같게 하는 안 (360px에서 메뉴 이름이 두 줄로 접힘)
- **누가·근거:** 사람이 요청하고 팀이 합의함 (2026-10-23)
- **영향:** `frontend/src/pages/Trips/Trips.jsx`(서준), `frontend/src/pages/Places/Places.jsx`(은희), `frontend/src/pages/Diary/Diary.jsx`(건용), `docs/DESIGN.md` 3절
- **다시 볼 조건:** 메뉴 이름이나 화면 제목을 다시 바꾸자는 의견이 나올 때
