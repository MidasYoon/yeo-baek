## D-005 설계 문서의 공통·개별 구분

- **결정:**
  - 공통 문서: `PRD`, `ARCHITECTURE`, `DATA-MODEL`, `API-SPEC`
  - 개별 문서: `SCREEN-SPEC`, `TEST-PLAN` (`TEST-PLAN`에는 기능 사이 연결·회귀 검사를 다루는 공통 절을 하나 둔다)
  - 모든 문서는 `docs/` 아래 한 파일로 두고, 기능별 내용은 그 파일 안의 담당자별 절에 쓴다.
  - 절 담당: 여행기록·`trips`는 서준, 여행지 정보·`places`·Home은 은희, 여행 다이어리·`diaries`·공통 레이아웃은 건용. `ARCHITECTURE` 초안은 공통 뼈대 담당인 건용이 쓴다.
- **배경:** 기능 3개를 담당자 3명이 나눠 맡아, 문서마다 누가 무엇을 쓰는지 정해야 했다.
- **이유:** 한 사람이 바꾸면 다른 기능이 깨질 수 있는 문서(테이블 연결 `trip_id`, Home이 쓰는 목록 API 등)는 공통으로 둔다. 자기 기능 안에서 끝나는 문서는 개별로 둔다. 기능별 파일로 나누지 않으면 `AGENTS.md`의 문서 목록을 바꾸지 않아도 된다.
- **다른 선택지:** 개별 문서를 기능별 파일로 나누는 안 (예: `docs/screen-spec/trips.md`). Git 충돌은 줄지만 `AGENTS.md`·`README.md`의 문서 목록을 고쳐야 한다.
- **누가·근거:** 사람이 AI의 제안 중 "한 파일 안에 담당자별 절" 안을 승인함
- **영향:** 같은 파일을 여러 명이 고치므로 Git 충돌이 날 수 있다. 공통 문서를 고칠 때는 팀에 먼저 알린다.
- **다시 볼 조건:** 같은 문서에서 Git 충돌이 자주 날 때
- **상태:** 대체됨 (D-007)
- **날짜:** 2026-10-19

## D-007 설계 문서의 공통·개별 구분과 고치는 규칙

- **결정:**
  - 공통 설계 문서: `PRD`, `ARCHITECTURE`, `DATA-MODEL`, `API-SPEC`
  - 개별 문서: `SCREEN-SPEC`, `TEST-PLAN` (`TEST-PLAN`에는 기능 사이 연결·회귀 검사를 다루는 공통 절을 하나 둔다)
  - 모든 문서는 `docs/` 아래 한 파일로 두고, 기능별 내용은 그 파일 안의 담당자별 절에 쓴다.

## D-011 화면과 서버의 연결 방식

- **결정:**
  - 프론트엔드(5173)는 Vite 개발 서버의 프록시를 거쳐 백엔드(8000)를 부른다.
  - API 주소는 `/api`로 시작한다. 정확한 주소는 `docs/API-SPEC.md`에서 정한다.
- **배경:** 두 포트가 달라 연결 방법을 정해야 했다. 화면 주소(D-012)와 API 주소가 같으면 프록시가 둘을 가를 수 없다.
- **이유:** `frontend/src/api/`의 세 파일에 서버 포트를 적지 않고 `/api/...` 상대 주소만 쓰면 된다. 새 라이브러리가 필요 없다.
- **다른 선택지:** FastAPI에서 CORS를 허용하고, 프론트엔드가 `http://localhost:8000` 같은 전체 주소를 쓰는 안

## D-015 장소·일기가 붙은 여행 지우기

- **결정:**
  - 장소나 일기가 하나라도 붙은 여행은 지울 수 없다.
  - DB: `places.trip_id`, `diaries.trip_id`를 `REFERENCES trips(id) ON DELETE RESTRICT`로 두고, `backend/database.py`가 연결할 때마다 `PRAGMA foreign_keys = ON`을 켠다.
  - `trips` 라우터: 지우기 전에 그 여행의 장소·일기 개수를 세고, 하나라도 있으면 지우지 않는다.

- **이유:** 다른 사람 기능의 데이터가 여행과 함께 사라지는 일을 막는다. DB가 막으면 라우터를 거치지 않는 길로도 지워지지 않고, 라우터가 개수를 세면 화면 안내 문구에 개수를 쓸 수 있다 (SCREEN-SPEC 3절 4번).
- **다른 선택지:** 연결된 장소·일기를 함께 지우는 안(`ON DELETE CASCADE`). DB 외래 키만 쓰는 안. 라우터 검사만 쓰는 안.
- **누가·근거:** 사람이 AI의 제안 중 고르고, 팀 합의로 보고 진행하라고 승인함

## D-016 DB 저장 규칙

## D-017 만든·고친 시각

- **결정:**
  - 모든 테이블에 `created_at`, `updated_at`을 둔다. 형식은 `TEXT`, `YYYY-MM-DD HH:MM:SS`, 한국 시각이다.
  - 처음에는 DB 기본값 `datetime('now', 'localtime')`이 넣고, 고칠 때는 그 테이블의 라우터가 `updated_at`을 넣는다. 트리거는 쓰지 않는다.
  - 기록용이며, 날짜(또는 날짜·시각)가 같을 때의 순서는 그대로 `id`로 가른다.
  - API 응답에 넣을지는 `docs/API-SPEC.md`에서 정한다.
- **배경:** PRD 공통 #2는 "만든 시각은 따로 저장하지 않는다"였다. 사람이 모든 테이블에 두 컬럼을 넣기로 했다.
- **이유:** 같은 초에 만든 줄은 `created_at`으로 순서를 가를 수 없어 `id`가 필요하다. `id`를 유지하면 PRD의 순서 규칙(L-11, H-05, R-D-008)을 바꾸지 않아도 된다. `CURRENT_TIMESTAMP`는 UTC로 들어가 한국 시각과 다르다.
- **다른 선택지:** 만든 시각을 저장하지 않는 안 (PRD 공통 #2 처음 안). 순서를 `created_at`으로 가르는 안. `updated_at`을 트리거로 바꾸는 안.
- **누가·근거:** 사람이 두 컬럼을 넣기로 정하고, 세부 방식은 AI의 제안대로 팀 합의로 보고 진행하라고 승인함
- **영향:** 세 라우터가 고칠 때마다 `updated_at`을 넣어야 한다. `docs/DATA-MODEL.md` 1~4절, `docs/PRD.md` 공통 #2·H-05, `docs/TEST-PLAN.md`(P-09)
- **다시 볼 조건:** 만든·고친 시각을 화면에 보여 주려 할 때
- **상태:** 유효
- **날짜:** 2026-10-21

## D-019 서버 검사와 오류 응답

- **결정:**
  - 서버도 화면과 같은 입력 규칙(필수, 글자 수, 날짜 형식, 기간 안, 시·도 17개, 기분 5개, 시각 형식)을 검사한다.

- **이유:** 화면을 거치지 않는 요청도 DB에 잘못된 값이 들어가지 않게 막는다 (D-015와 같은 생각). 기본 모양을 그대로 쓰면 공통 파일 `backend/main.py`에 오류 처리기를 따로 넣지 않아도 된다. 개수를 409에 넣으면 개수만 세는 API를 따로 만들지 않아도 된다.
- **다른 선택지:** 화면만 검사하는 안. 팀 공통 오류 모양을 따로 만드는 안. 개수만 세는 API를 따로 두는 안.
- **누가·근거:** 사람이 AI의 추천안대로 진행하라고 승인함 (PLAN P-08)
- **영향:** 세 라우터의 검사 코드. FastAPI 자동 422의 `detail`은 목록이고, 직접 돌려주는 404·409의 `detail`은 글자나 객체라 모양이 다르다. `docs/API-SPEC.md` 1절, `docs/TEST-PLAN.md`(P-09)
- **다시 볼 조건:** 화면이 422를 받아 칸별 안내를 보여야 할 때

## D-021 공백만 적은 값과 서버 `422`를 받았을 때

- **결정:**
  - 공백만 적은 필수 글자 값(여행명·여행지, 장소 이름, 일기 제목)은 서버가 비운 것으로 보고 `422`를 돌려준다.
