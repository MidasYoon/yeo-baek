# API 명세 (API-SPEC)

> 화면과 서버가 주고받는 약속(주소, 메서드, 요청·응답 모양)을 적는다. 저장하는 필드의 이름과 뜻은 `docs/DATA-MODEL.md`, 구조는 `docs/ARCHITECTURE.md`를 따른다.
> 한 파일 안에 담당자별 절로 쓰고, 담당자별 절도 팀이 합의한 뒤에만 고친다 (D-007).
> 기능별 절(2~4, 6~9)은 모두 같은 목차 1~7을 따른다. 근거가 되는 PRD·SCREEN-SPEC·DATA-MODEL 번호를 괄호로 적는다.
> "제안"이나 "확인 필요"가 붙은 내용은 확정이 아니다.

### 사진 올리기와 보기 (D-033)

사진은 두 단계로 저장한다. ① 화면이 사진 파일만 먼저 올려 파일 이름을 받는다. ② 여행·장소·일기를 저장할 때 JSON 본문에 그 파일 이름을 넣는다.

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `POST` | `/api/uploads` | 사진 한 장 올리기. `multipart/form-data`의 `file` 칸에 넣는다 | `201` + `{"filename": "…"}` | `422` |
| `GET` | `/api/uploads/{filename}` | 사진 보기. 화면은 `<img src="/api/uploads/{filename}">`로 쓴다 | `200` + 사진 파일 | `404` |

```json
{ "filename": "3f2a9c0d4b1e4f6a8d7c2b5e1a0f9c11.jpg" }
```

| 항목 | 규칙 |
| --- | --- |
| 받는 형식 | jpg·jpeg·png·webp. 확장자와 `Content-Type`(`image/jpeg`·`image/png`·`image/webp`)이 모두 맞아야 한다. 아니면 `422` |
| 용량 | 한 장 5MB 이하. 넘으면 `422` |
| 파일 이름 | 서버가 uuid 32자 + 확장자로 새로 붙인다. 원래 파일 이름은 쓰지도 저장하지도 않는다 |
| 저장 위치 | `backend/uploads/` (DATA-MODEL 1절 "사진 저장") |
| 한 번에 올리는 수 | 한 장. 장소 사진 여러 장은 한 장씩 여러 번 부른다 (AI 제안) |
| 서버 쪽 | 올리기는 `backend/routers/uploads.py`(공통, 건용 관리). 보기는 `backend/main.py`가 `backend/uploads/` 폴더를 `/api/uploads`에 연결한다 (ARCHITECTURE) |
| 부르는 곳 | `frontend/src/api/`의 기능별 파일마다 사진 올리기 함수를 둔다. 공통 부르기 코드를 기능별 파일에 각각 두는 D-027을 따른다 (AI 제안) |

**여행·장소·일기 본문의 사진 칸 (세 기능 공통)**
- 사진 칸에는 `POST /api/uploads`가 돌려준 `filename`만 넣는다. 서버는 이름 꼴(uuid 32자 + 허용 확장자)이 맞고 `backend/uploads/`에 실제로 있는 파일인지 검사한다. 아니면 `422`.
- 사진이 없으면 `null`(여행·일기) 또는 `[]`(장소)이다.
- `PUT`은 폼 전체를 보내므로(D-018) 사진 칸도 늘 보낸다. 저장에 성공하면, 전에 있던 사진 중 새 본문에 없는 것은 라우터가 `backend/uploads/`에서도 지운다.
- `DELETE`에 성공하면 그 기록의 사진 파일도 라우터가 지운다. 여행이 장소·일기 때문에 `409`면 사진도 지우지 않는다.
- 올리기만 하고 저장하지 않은 사진(폼을 취소함 등)은 어디에도 연결되지 않은 채 `backend/uploads/`에 남는다. 이번 MVP의 한계로 두고 지우지 않는다 (PLAN "남은 문제").
- 회원 프로필사진(7절)도 같은 방법으로 올린다. 가입 폼에서도 올려야 하므로 `POST /api/uploads`는 로그인 없이 부를 수 있다 (D-042).

### 로그인 (D-042)

로그인하면 서버가 세션 토큰을 쿠키로 준다. 그 뒤 요청마다 브라우저가 쿠키를 보내고, 서버는 `sessions` 테이블에서 그 토큰의 회원을 찾는다 (DATA-MODEL 7절). 쿠키 값과 모양은 AI 제안이다.

| 항목 | 규칙 |
| --- | --- |
| 쿠키 | 이름 `yeoback_session`, 값은 `sessions.token`. `HttpOnly`(화면 코드가 읽지 못함), `SameSite=Lax`, `Path=/`, `Max-Age=604800`(7일). `Secure`는 붙이지 않는다(개발용 `http://localhost`) |
| 쿠키를 주는 때 | 가입 성공(`POST /api/users`), 로그인 성공(`POST /api/users/login`) |
| 쿠키를 지우는 때 | 로그아웃(`POST /api/users/logout`). 같은 이름으로 `Max-Age=0`을 보낸다 |
| 로그인한 것으로 보는 때 | 쿠키가 있고, 그 토큰의 세션이 있고, `expires_at`이 지나지 않았을 때. 아니면 로그인하지 않은 것이다 (지난 세션 줄은 지운다) |
| 로그인 없이 부르는 API | 모든 `GET`, `POST /api/uploads`, `POST /api/recommend`, `POST /api/users`, `POST /api/users/login`, `POST /api/users/logout` |
| 로그인해야 부르는 API | 위 밖의 모든 `POST`·`PUT`·`DELETE`: 여행·장소·일기 만들기·고치기·지우기, `PUT /api/users/me`, 좋아요, 댓글 쓰기·지우기. 로그인하지 않았으면 `401` |
| 주인만 부르는 API | 여행 고치기·지우기(그 여행의 주인), 장소·일기 만들기·고치기·지우기(그 장소·일기가 속한 여행의 주인), 댓글 지우기(쓴 회원). 아니면 `403`. 주인이 없는 여행(`user_id`가 `null`)은 누구에게나 `403`이다 |
| 검사 순서 | 로그인 `401` → 본문 `422` → 없는 `id` `404` → 주인 `403` → `409` (D-029 순서 앞에 `401`, `404` 뒤에 `403`을 끼운다, AI 제안) |
| `GET` 응답과 로그인 | `GET`은 로그인 없이 같은 모양으로 돌려준다. 여행 객체의 `liked`(2절)만 로그인한 회원에 따라 다르다 |
| 화면이 막기 | 화면은 로그인하지 않았거나 주인이 아니면 버튼을 숨긴다 (SCREEN-SPEC 8절). `401`·`403`은 그 검사를 지나친 요청을 막는 마지막 단계다 (D-019와 같은 생각) |

- 비밀번호, `password_hash`, 세션 토큰은 응답 본문과 서버 로그에 넣지 않는다 (D-042).

### 비어 있을 때

| 경우 | 응답 | 근거 |
| --- | --- | --- |
| 목록에 항목이 없음 | `200` + `[]` | D-020 |
| "최근 1개"가 없음 | `200` + `null` | D-020 |

- 404로 돌려주지 않는다. 화면이 "없음"(빈 상태)과 오류를 가를 수 있게 하기 위해서다.

### 오류 응답

서버도 화면과 같은 입력 규칙을 검사한다 (D-019). 기능별 규칙은 각 절에 적는다.
오류 응답은 FastAPI 기본 모양 `{"detail": ...}`을 그대로 쓴다.

| 상태 코드 | 언제 | `detail` 모양 | 근거 |
| --- | --- | --- | --- |
| `422` | 입력 규칙을 어김 (필수, 글자 수, 형식, 기간 안, 정해진 값 목록) | FastAPI가 자동으로 막은 것은 목록, 라우터가 직접 막은 것(기간 안 등)은 글자 | D-019 |
| `404` | 주소의 `{id}`에 해당하는 것이 없음 | 글자. 예: `"여행을 찾을 수 없어요"` (AI 제안 문구) | D-019, SCREEN-SPEC 3절 6번 |
| `409` | 장소·일기 때문에 여행을 지우거나 기간을 고칠 수 없음 | 객체 `{"place_count": N, "diary_count": M}` | D-015, D-019 |
| `401` | 로그인해야 하는 API를 로그인하지 않고 부름. 로그인할 때 아이디·비밀번호가 틀림 | 글자. `"로그인이 필요해요"`, 로그인 실패는 `"아이디 또는 비밀번호가 맞지 않아요"` (AI 제안 문구) | D-042 |
| `403` | 남의 여행·장소·일기를 고치거나 지우려 함, 남의 댓글을 지우려 함, 회원정보수정의 지금 비밀번호가 틀림 | 글자. `"내 여행만 고칠 수 있어요"`, `"내 댓글만 지울 수 있어요"`, `"지금 비밀번호가 맞지 않아요"` (AI 제안 문구) | D-042 |
| `409` | 가입할 때 이미 있는 아이디 | 글자 `"이미 쓰는 아이디예요"` (AI 제안 문구). 여행의 `409`와 달리 `detail`이 글자다 | D-042 |

409 예 (장소 2곳, 일기 1편이 붙은 여행을 지우려 함):

```json
{ "detail": { "place_count": 2, "diary_count": 1 } }
```

- 409의 개수는 여행 지우기에서는 붙어 있는 장소·일기 개수, 기간 수정에서는 새 기간 밖의 장소·일기 개수다.
- 409 안내 문구는 화면이 개수로 만든다 (SCREEN-SPEC 3절 4번). 서버는 문구를 보내지 않는다.
- 여행 상세에서 "삭제"를 누를 때의 안내는 화면이 이미 불러온 장소·일기 목록의 개수로 먼저 보여 준다. 409는 그 검사를 지나친 요청을 막는 마지막 단계다 (D-019).
- 요청 본문의 `trip_id`가 없는 여행이면 `422`로 본다. 주소의 `{id}`가 아니기 때문이다 (AI 제안).

## 2. `trips` (담당: 서준)

> 근거: D-001, PRD 2절, SCREEN-SPEC 3절, DATA-MODEL 2절. 라우터는 `backend/routers/trips.py`, 부르는 곳은 `frontend/src/api/trips.js`.

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/trips` | 여행 목록 | `200` + 여행 객체 목록 | — |
| `GET` | `/api/trips/{id}` | 여행 하나 | `200` + 여행 객체 | `404` |
| `POST` | `/api/trips` | 여행 만들기 | `201` + 만든 여행 객체 | `401`, `422` |
| `PUT` | `/api/trips/{id}` | 여행 고치기 | `200` + 고친 여행 객체 | `401`, `404`, `422`, `403`, `409` |
| `DELETE` | `/api/trips/{id}` | 여행 지우기 | `204` | `401`, `404`, `403`, `409` |

- `401`·`403`은 D-042로 더했다 (1절 "로그인").

### 2. 여행 객체

모든 응답에서 여행은 같은 모양이다. 목록도 여행 정보(`info`)까지 다 넣는다 (AI 제안. 목록 화면은 `info`를 보이지 않지만 모양을 하나로 두면 `api/trips.js`가 간단하다).

```json
{
  "id": 1,
  "name": "부산 바다 여행",
  "destination": "부산",
  "start_date": "2026-05-01",
  "end_date": "2026-05-04",
  "info": "친구와 3박 4일",
  "photo": "3f2a9c0d4b1e4f6a8d7c2b5e1a0f9c11.jpg",
  "user_id": 1,
  "user_nickname": "여행하는 곰",
  "user_profile_photo": null,
  "like_count": 3,
  "liked": true,
  "comment_count": 2,
  "created_at": "2026-10-21 14:05:00",
  "updated_at": "2026-10-21 14:05:00"
}
```

| 필드 | 뜻 | 비었을 때 | 근거 |
| --- | --- | --- | --- |
| `id` | 여행 번호 | — | DATA-MODEL 2절 |
| `name` | 여행명 | — | DATA-MODEL 2절 |
| `destination` | 여행지 | — | DATA-MODEL 2절 |
| `start_date`, `end_date` | 시작일, 종료일 (`YYYY-MM-DD`) | — | DATA-MODEL 2절 |
| `info` | 여행 정보 (자유 메모) | `null` | DATA-MODEL 2절, 1절 "주고받는 값" |
| `photo` | 대표사진 파일 이름. 화면은 `/api/uploads/{photo}`로 보인다 | `null` | DATA-MODEL 2절, D-033 |
| `user_id` | 주인의 회원 번호. 화면은 로그인한 회원의 `id`(7절 `GET /api/users/me`)와 견주어 수정·삭제·추가 버튼을 보인다 | `null` (주인 없는 여행) | DATA-MODEL 2절, D-042 |
| `user_nickname` | 주인의 지금 닉네임 (`users.nickname`을 붙여 넣음) | `null` (주인 없는 여행) | DATA-MODEL 6절, D-042, AI 제안 |
| `user_profile_photo` | 주인의 지금 프로필사진 파일 이름 (`users.profile_photo`를 붙여 넣음). 화면은 `/api/uploads/{이름}`으로 작성자 사진을 보인다 | `null` (사진 없는 회원, 주인 없는 여행) | DATA-MODEL 6절, D-047, 이름은 AI 제안 |
| `like_count` | 이 여행의 좋아요 수 | `0` | DATA-MODEL 8절, D-042, AI 제안 |
| `liked` | 지금 로그인한 회원이 좋아요를 눌렀는지. 로그인하지 않았으면 `false` | `false` | D-042, AI 제안 |
| `comment_count` | 이 여행의 댓글 수. 여행 목록 카드가 보인다 | `0` | DATA-MODEL 9절, D-045, 이름은 AI 제안 |
| `created_at`, `updated_at` | 만든·고친 시각 | — | D-020 |

- `user_id`·`user_nickname`·`like_count`·`liked`는 D-042로, `comment_count`는 D-045로, `user_profile_photo`는 D-047로 더한 칸이다. 칸이 늘기만 했으므로 여행 객체를 쓰는 다른 화면(장소·다이어리의 여행 select, Home)은 고치지 않아도 된다.
- 여행 상세의 "댓글 N"은 `comment_count`를 쓰지 않고 댓글 목록(9절)의 길이로 센다. 댓글을 쓰고 지울 때 바로 바뀌어야 하기 때문이다 (D-044, D-045).

### 3. 요청 본문과 서버 검사

`POST`와 `PUT`은 같은 본문을 보낸다. `PUT`도 폼의 값 전체를 보낸다 (D-018).

```json
{
  "name": "부산 바다 여행",
  "destination": "부산",
  "start_date": "2026-05-01",
  "end_date": "2026-05-04",
  "info": "친구와 3박 4일",
  "photo": "3f2a9c0d4b1e4f6a8d7c2b5e1a0f9c11.jpg"
}
```

서버는 아래 규칙을 어기면 저장하지 않고 `422`를 돌려준다 (D-019).

| 필드 | 필수 | 서버가 검사하는 규칙 | 근거 |
| --- | --- | --- | --- |
| `name` | 필수 | 20자 이하. 공백만 적으면 비운 것으로 본다 (D-021) | PRD 2절 3번, R-T-018 |
| `destination` | 필수 | 20자 이하. 공백만 적으면 비운 것으로 본다 (D-021) | PRD 2절 3번, R-T-018 |
| `start_date` | 필수 | `YYYY-MM-DD`이고 실제 있는 날짜 | PRD 2절 3번 |
| `end_date` | 필수 | `YYYY-MM-DD`이고 실제 있는 날짜. `start_date`보다 빠를 수 없다. 같은 날은 된다 | PRD 2절 3번, R-T-005 |
| `info` | 선택 | 글자 수 제한 없음. 빼거나 `null`이면 비운 것 | PRD 2절 3번 |
| `photo` | 선택 | 0~1장. 빼거나 `null`이면 사진 없음. 1절 "사진 올리기와 보기"의 사진 칸 규칙 | PRD 2절 3번, R-T-020, D-033 |

- `id`, `created_at`, `updated_at`은 본문에 넣지 않는다 (1절 "주고받는 값").
- `user_id`, `user_nickname`, `user_profile_photo`, `like_count`, `liked`, `comment_count`도 본문에 넣지 않는다. 넣어도 서버가 쓰지 않는다. 주인은 로그인한 회원으로 정한다 (D-042).
- 글자 값은 앞뒤 공백을 빼고 저장한다. 글자 수도 뺀 뒤 센다. 선택 항목을 비우거나 공백만 적으면 `null`이다 (D-029).

### 4. API별 규칙

- 만들기·고치기·지우기는 로그인해야 하고, 고치기·지우기는 주인만 한다. 검사 순서는 1절 "로그인"을 따른다 (D-042).

**`GET /api/trips` — 여행 목록**
- 순서: `start_date`가 늦은 것이 앞, 같으면 `id`가 큰 것이 앞 (R-T-007, R-T-016, DATA-MODEL 2절 2번).
- 여행이 없으면 `200` + `[]` (D-020).

**`GET /api/trips/{id}` — 여행 하나**
- 없는 `id`면 `404` (SCREEN-SPEC 3절 5번 "찾을 수 없는 여행이에요").

**`POST /api/trips` — 여행 만들기**
- 성공하면 `201`과 만든 여행 객체를 돌려준다. 화면은 이 객체의 `id`로 새 여행의 상세(`/trip/:id`)로 간다 (SCREEN-SPEC 3절 3번).
- 로그인하지 않았으면 `401`. 만든 여행의 `user_id`는 로그인한 회원이다 (D-042).

**`PUT /api/trips/{id}` — 여행 고치기**
- 검사 순서: 로그인하지 않았으면 `401` → 입력 규칙을 어기면 `422` → 없는 `id`면 `404` → 주인이 아니면 `403` → 기간 밖 장소·일기가 있으면 `409` (D-029, D-042).
- 기간 검사: 그 여행의 `places.visit_date`나 `diaries.date` 중 새 `start_date`~`end_date` 밖의 것을 센다. 하나라도 있으면 고치지 않고 `409`를 돌려준다 (R-T-017, DATA-MODEL 2절 3번).

  ```json
  { "detail": { "place_count": 1, "diary_count": 0 } }
  ```

  화면은 이 개수로 종료일 칸 아래 안내를 만든다. 0인 쪽은 빼고 적는다 (SCREEN-SPEC 3절 4번).
- 성공하면 라우터가 `updated_at`을 지금 시각으로 바꾸고, `200`과 고친 여행 객체를 돌려준다 (D-017).
- 대표사진을 바꾸거나 뺐으면 전 사진 파일을 지운다 (1절 "사진 올리기와 보기").

**`DELETE /api/trips/{id}` — 여행 지우기**
- 검사 순서: 로그인하지 않았으면 `401` → 없는 `id`면 `404` → 주인이 아니면 `403` → 붙은 장소·일기가 있으면 `409` (D-029, D-042).
- 그 여행의 장소 개수와 일기 개수를 센다. 하나라도 있으면 지우지 않고 `409`를 돌려준다 (R-T-012, D-015).

  ```json
  { "detail": { "place_count": 2, "diary_count": 1 } }
  ```

- 화면은 "삭제"를 누를 때 상세에 이미 불러온 장소·일기 목록의 개수로 먼저 안내한다. `409`는 그 검사를 지나친 요청을 막는다 (D-019).
- DB도 외래 키(`ON DELETE RESTRICT`)로 한 번 더 막는다 (D-015).
- 성공하면 대표사진 파일도 지우고 `204`, 본문 없음 (D-033).
- 좋아요·댓글은 막지 않는다. 여행을 지우면 DB가 그 여행의 좋아요·댓글을 함께 지운다 (D-042, DATA-MODEL 8·9절).

## 3. `places` (담당: 은희)

> 근거: D-002, D-006, D-014, D-036, D-043, PRD 3절, SCREEN-SPEC 4절, DATA-MODEL 3절. 라우터는 `backend/routers/places.py`, 부르는 곳은 `frontend/src/api/places.js`.

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/places?trip_id={tripId}` | 여행별 장소 목록 | `200` + 장소 객체 목록 | `422` |
| `GET` | `/api/places/recent` | 모든 여행에 걸친 최근 장소 1개 | `200` + 장소 객체 또는 `null` | — |
| `GET` | `/api/places/page?page={page}&size={size}` | 전체 보기 한 페이지: 모든 여행의 장소를 최신순으로 (D-034) | `200` + `{ "items": [...], "total": n }` | `422` |
| `GET` | `/api/places/{id}` | 장소 하나 | `200` + 장소 객체 | `404` |
| `POST` | `/api/places` | 장소 추가 | `201` + 만든 장소 객체 | `401`, `422`, `403` |
| `PUT` | `/api/places/{id}` | 장소 수정 | `200` + 고친 장소 객체 | `401`, `404`, `422`, `403` |
| `DELETE` | `/api/places/{id}` | 장소 삭제 | `204` | `401`, `404`, `403` |

- `/api/places/recent`, `/api/places/page`는 라우터에서 `/api/places/{id}`보다 먼저 등록한다 (1절 "주소 규칙").
- 추가·수정·삭제는 로그인해야 하고, 그 장소가 속한 여행(`POST`는 본문의 `trip_id`)의 주인만 한다. 검사 순서는 로그인 `401` → 본문 `422`(없는 여행 포함) → 없는 `id` `404` → 주인 `403`이다 (1절 "로그인", D-042). 장소 객체와 조회 API는 바뀌지 않는다.

### 2. 장소 객체

모든 응답에서 장소는 같은 모양이다. 전체 보기 응답(`/page`)의 `items`에만 `trip_name`이 더 붙는다 (4번, D-034).

```json
{
  "id": 3,
  "trip_id": 1,
  "region": "부산",
  "name": "해운대",
  "visit_date": "2026-05-02",
  "memo": "바람이 셌음",
  "rating": 4,
  "photos": ["a1b2c3d4e5f60718293a4b5c6d7e8f90.jpg", "0f9e8d7c6b5a49382716f5e4d3c2b1a0.png"],
  "lat": 35.1587,
  "lng": 129.1604,
  "kakao_place_id": "7990409",
  "created_at": "2026-10-21 14:10:00",
  "updated_at": "2026-10-21 14:10:00"
}
```

| 필드 | 뜻 | 비었을 때 | 근거 |
| --- | --- | --- | --- |
| `id` | 장소 번호 | — | DATA-MODEL 3절 |
| `trip_id` | 이 장소가 속한 여행 | — | DATA-MODEL 3절 |
| `region` | 지역. 시·도 17개 이름 그대로 | — | DATA-MODEL 3절, D-016 |
| `name` | 장소 이름 | — | DATA-MODEL 3절 |
| `visit_date` | 방문 날짜 (`YYYY-MM-DD`) | — | DATA-MODEL 3절 |
| `memo` | 메모 | `null` | DATA-MODEL 3절, 1절 "주고받는 값" |
| `rating` | 별점 1~5 (정수) | `null` (D-043 전에 넣은 장소) | DATA-MODEL 3절, D-043 |
| `photos` | 사진 파일 이름 목록 (0~4개). `place_photos.id`가 작은 것이 앞 | `[]` | DATA-MODEL 5절, D-033 |
| `lat`, `lng` | 위도·경도 (숫자) | `null` (D-036 전에 넣은 장소) | DATA-MODEL 3절, D-036 |
| `kakao_place_id` | 카카오 장소 id (글자) | `null` (D-036 전에 넣은 장소) | DATA-MODEL 3절, D-036 |
| `created_at`, `updated_at` | 만든·고친 시각 | — | D-020 |

- 핀은 화면이 `lat`·`lng`에 찍고, 같은 `kakao_place_id`끼리 묶는다. `lat`·`lng`가 `null`이면 `region`의 시·도 가운데에 찍는다 (R-P-026, D-036).
- 핀 위의 개수는 화면이 목록에서 같은 곳(카카오맵) 또는 같은 `region`(그림 지도)을 세어 보인다. 개수만 돌려주는 API는 두지 않는다 (R-P-006, R-P-026, D-014, AI 제안).
- 칸이 늘기만 했으므로 장소 객체를 쓰는 다른 화면(여행 상세, Home)은 고치지 않아도 된다 (D-036). `rating`(D-043)도 칸이 늘기만 한다. 초롱 줄은 `PlaceCard`가 보인다. Home은 `rating`을 쓰지 않는다.
- `photos`는 `place_photos` 테이블에서 모아 넣는다. 사진만 따로 가져오는 API는 두지 않는다 (AI 제안).

### 3. 요청 본문과 서버 검사

`POST` 본문:

```json
{
  "trip_id": 1,
  "region": "부산",
  "name": "해운대",
  "visit_date": "2026-05-02",
  "memo": "바람이 셌음",
  "rating": 4,
  "photos": ["a1b2c3d4e5f60718293a4b5c6d7e8f90.jpg"],
  "lat": 35.1587,
  "lng": 129.1604,
  "kakao_place_id": "7990409"
}
```

`PUT` 본문은 `trip_id`를 뺀 나머지 전체다. 수정 폼에는 여행 select가 없어 장소의 여행을 바꿀 수 없기 때문이다 (SCREEN-SPEC 1절 "장소·일기 폼 화면의 여행", AI 제안).

서버는 아래 규칙을 어기면 저장하지 않고 `422`를 돌려준다 (D-019).

| 필드 | 필수 | 서버가 검사하는 규칙 | 근거 |
| --- | --- | --- | --- |
| `trip_id` | 필수 (`POST`만) | 있는 여행의 `id`. 없는 여행이면 `422` (1절 "오류 응답") | DATA-MODEL 3절 |
| `region` | 필수 | 시·도 17개 이름 중 하나: 서울, 부산, 대구, 인천, 광주, 대전, 울산, 세종, 경기, 강원, 충북, 충남, 전북, 전남, 경북, 경남, 제주 | PRD 3절 3번, D-016 |
| `name` | 필수 | 글자 수 제한 없음 (D-036, 전에는 20자). 공백만 적으면 비운 것으로 본다 (D-021) | PRD 3절 3번 |
| `visit_date` | 필수 | `YYYY-MM-DD`이고 실제 있는 날짜. 그 여행의 `start_date`~`end_date` 안 | PRD 3절 3번, L-05 |
| `memo` | 선택 | 20자 이하. 빼거나 `null`이면 비운 것 | PRD 3절 3번 |
| `rating` | 필수 | 1~5 정수. 빼거나 `null`이거나, 범위 밖(0, 6)·소수(3.5)·숫자가 아닌 글자(`"abc"`)면 `422` | PRD 3절 3번, D-043 |
| `photos` | 선택 | 파일 이름 목록 0~4개. 5개 이상이거나 같은 이름이 두 번 있으면 `422`. 빼면 `[]`. 1절 "사진 올리기와 보기"의 사진 칸 규칙 | PRD 3절 3번, R-P-022, D-033 |
| `lat` | 선택 | 숫자, 33 이상 39 이하. 빼면 `null` | D-036 |
| `lng` | 선택 | 숫자, 124 이상 132 이하. 빼면 `null` | D-036 |
| `kakao_place_id` | 선택 | 숫자로만 된 글자 1~20자. 빼거나 비우면 `null` | D-036, AI 제안 |

- `lat`·`lng`·`kakao_place_id`는 셋 다 있거나 셋 다 없어야 한다. 하나라도 어긋나면 `422` (D-036. `kakao_place_id`까지 묶는 것은 AI 제안).
- `rating`은 `POST`·`PUT` 모두 필수다. DB에는 비어 있는 기존 장소가 있지만, 그 장소를 고칠 때도 `rating`을 넣어야 저장된다 (R-P-029, D-043).
- 장소 검색은 화면에서 필수지만 서버는 세 칸이 없는 것도 받는다. 서버는 `region`을 좌표로 다시 계산하지 않고 17개 이름인지만 본다 (D-036).

- 기간 검사에 쓰는 여행은 `POST`는 본문의 `trip_id`, `PUT`은 그 장소에 저장된 `trip_id`의 여행이다.
- 메모의 "한 줄"은 입력 칸 모양으로 지킨다. 서버는 줄바꿈을 검사하지 않는다 (AI 제안).
- `id`, `created_at`, `updated_at`은 본문에 넣지 않는다 (1절 "주고받는 값").
- 글자 값은 앞뒤 공백을 빼고 저장한다. 글자 수도 뺀 뒤 센다. 선택 항목을 비우거나 공백만 적으면 `null`이다 (D-029).

### 4. API별 규칙

**`GET /api/places?trip_id={tripId}` — 여행별 장소 목록**
- 순서: `visit_date`가 오래된 것이 앞, 같으면 `id`가 작은 것이 앞 (L-11, DATA-MODEL 3절 2번). 여행 상세는 이 순서 그대로, 장소 화면은 뒤집어 최신순으로 보인다 (R-P-009, D-034).
- 장소가 없으면 `200` + `[]` (D-020).
- `trip_id`를 빼면 `422` (FastAPI 자동).
- 없는 여행의 `trip_id`면 `200` + `[]` (AI 제안). 화면은 주소의 여행 번호가 여행 목록에 없으면 "전체 여행"으로 시작하므로 이 API를 부르지 않는다 (SCREEN-SPEC 4절 5번, D-034).
- 페이지를 나누지 않는다. 여행을 고른 화면과 여행 상세가 이 목록 전체를 쓴다 (D-034).

**`GET /api/places/page?page={page}&size={size}` — 전체 보기 한 페이지 (D-034)**
- 모든 여행의 장소를 `visit_date`가 늦은 것, 같으면 `id`가 큰 것부터 줄 세워 `page`번째 묶음(`size`곳)을 돌려준다.
- `page`는 1부터, 빼면 1. `size`는 1~50, 빼면 10. 숫자가 아니거나 범위를 벗어나면 `422` (FastAPI 자동, AI 제안).
- 응답: `{ "items": [장소 객체…], "total": 13 }`. `items`의 장소 객체에는 그 여행의 `name`이 `trip_name`으로 더 붙는다. `total`은 모든 여행의 장소 개수다 (AI 제안).
- 마지막 페이지보다 큰 `page`면 `items`는 `[]`이고 `total`은 그대로다. 화면은 `total`로 마지막 페이지를 계산해 그 페이지를 다시 부른다 (SCREEN-SPEC 1절 "잘못된 페이지 번호").
- 장소가 하나도 없으면 `200` + `{ "items": [], "total": 0 }` (D-020).

**`GET /api/places/recent` — 최근 장소 1개**
- 모든 여행에서 `visit_date`가 늦은 것, 같으면 `id`가 큰 것 1개 (R-P-013, H-02, H-05, DATA-MODEL 3절 2번).
- 장소가 하나도 없으면 `200` + `null` (D-020).

**`GET /api/places/{id}` — 장소 하나**
- 수정 폼 화면(`/place/:id/edit`)이 쓴다. 없는 `id`면 `404` (SCREEN-SPEC 4절 5번 "찾을 수 없는 장소예요").
- 폼에 보일 여행 이름·기간은 응답의 `trip_id`로 `GET /api/trips/{id}`를 불러 얻는다 (2절 5번).

**`POST /api/places` — 장소 추가**
- 성공하면 `201`과 만든 장소 객체를 돌려준다. 화면은 `/place?trip=:tripId` 목록으로 돌아간다 (SCREEN-SPEC 4절 3번).

**`PUT /api/places/{id}` — 장소 수정**
- 검사 순서: 로그인하지 않았으면 `401` → 입력 규칙을 어기면 `422` → 없는 `id`면 `404` → 그 여행의 주인이 아니면 `403` (D-029, D-042).
- 성공하면 라우터가 `updated_at`을 지금 시각으로 바꾸고, `200`과 고친 장소 객체를 돌려준다 (D-017).
- `photos`는 본문 목록으로 통째로 바꾼다. 새 목록에 없는 사진은 `place_photos` 줄과 파일을 지우고, 새로 생긴 이름은 줄을 더한다. 남는 사진의 순서는 그대로다 (D-033, AI 제안).

**`DELETE /api/places/{id}` — 장소 삭제**
- 로그인하지 않았으면 `401` → 없는 `id`면 `404` → 그 여행의 주인이 아니면 `403` (D-042). 성공하면 그 장소의 사진 줄과 파일도 지우고 `204`, 본문 없음 (R-P-011, D-033, DATA-MODEL 5절).

## 4. `diaries` (담당: 건용)

> 근거: D-003, D-016, PRD 4절, SCREEN-SPEC 5절, DATA-MODEL 4절. 라우터는 `backend/routers/diaries.py`, 부르는 곳은 `frontend/src/api/diaries.js`.

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/diaries?trip_id={tripId}` | 여행별 일기 목록 | `200` + 일기 객체 목록 | `422` |

| `GET` | `/api/diaries/page?page={page}&size={size}` | 전체 보기 한 페이지: 모든 여행의 일기를 최신순으로 (D-034) | `200` + `{ "items": [...], "total": n }` | `422` |

- `/api/diaries/recent`는 라우터에서 `/api/diaries/{id}`보다 먼저 등록한다 (1절 "주소 규칙").
- 쓰기·고치기·지우기는 로그인해야 하고, 그 일기가 속한 여행(`POST`는 본문의 `trip_id`)의 주인만 한다. 검사 순서는 3절과 같다 (1절 "로그인", D-042). 일기 객체와 조회 API는 바뀌지 않는다.

### 2. 일기 객체

모든 응답에서 일기는 같은 모양이다. 전체 보기 응답(`/page`)의 `items`에만 `trip_name`이 더 붙는다 (4번, D-034).

```json
{
  "id": 5,
  "trip_id": 1,
  "date": "2026-05-02",
  "time": "21:30",
  "title": "해운대 밤바다",
  "body": "파도 소리가 생각보다 컸다.",
  "mood": "행복",
  "photo": "7c6b5a49382716f5e4d3c2b1a0f9e8d7.webp",
  "created_at": "2026-10-21 14:20:00",
  "updated_at": "2026-10-21 14:20:00"
}
```

| 필드 | 뜻 | 비었을 때 | 근거 |
| --- | --- | --- | --- |
| `id` | 일기 번호 | — | DATA-MODEL 4절 |
| `trip_id` | 이 일기가 속한 여행 | — | DATA-MODEL 4절 |
| `date` | 날짜 (`YYYY-MM-DD`) | — | DATA-MODEL 4절 |
| `time` | 시각. `HH:MM` 24시간 | — | DATA-MODEL 4절, D-016, D-020 |
| `title` | 제목 | — | DATA-MODEL 4절 |
| `body` | 본문 | `null` | DATA-MODEL 4절, 1절 "주고받는 값" |
| `mood` | 기분. 기분 이름 5개 중 하나 | — | DATA-MODEL 4절, D-016 |
| `photo` | 사진 파일 이름 | `null` | DATA-MODEL 4절, D-033 |
| `created_at`, `updated_at` | 만든·고친 시각 | — | D-020 |

- `time`을 `오전/오후 H:MM`으로 바꿔 보이는 일, 폼의 오전/오후·시·분 select 3개를 `HH:MM`으로 합치는 일은 화면(`frontend/src/pages/Diary/`)에서만 한다 (D-020, SCREEN-SPEC 5절 2번).
- `mood`에 맞는 이모지를 보이는 일도 화면이 한다. 응답에 이모지는 없다 (D-016).
- 같은 날짜 일기를 날짜 제목 아래 묶는 일은 화면이 한다. API는 묶지 않은 목록을 순서대로 돌려준다 (R-D-018, AI 제안).

### 3. 요청 본문과 서버 검사

`POST` 본문:

```json
{
  "trip_id": 1,
  "date": "2026-05-02",
  "time": "21:30",
  "title": "해운대 밤바다",
  "body": "파도 소리가 생각보다 컸다.",
  "mood": "행복",
  "photo": "7c6b5a49382716f5e4d3c2b1a0f9e8d7.webp"
}
```

`PUT` 본문은 `trip_id`를 뺀 나머지 전체다. 고치기 폼에는 여행 select가 없어 일기의 여행을 바꿀 수 없기 때문이다 (SCREEN-SPEC 1절 "장소·일기 폼 화면의 여행", AI 제안. 3절과 같다).

서버는 아래 규칙을 어기면 저장하지 않고 `422`를 돌려준다 (D-019).

| 필드 | 필수 | 서버가 검사하는 규칙 | 근거 |
| --- | --- | --- | --- |
| `trip_id` | 필수 (`POST`만) | 있는 여행의 `id`. 없는 여행이면 `422` (1절 "오류 응답") | DATA-MODEL 4절 |
| `date` | 필수 | `YYYY-MM-DD`이고 실제 있는 날짜. 그 여행의 `start_date`~`end_date` 안 | PRD 4절 3번, R-D-003 |
| `time` | 필수 | `HH:MM`. 시는 `00`~`23`, 분은 `00`~`59`, 두 자리씩 | DATA-MODEL 4절, D-016 |
| `title` | 필수 | 50자 이하. 공백만 적으면 비운 것으로 본다 (D-021) | PRD 4절 3번, R-D-005 |
| `body` | 선택 | 글자 수 제한 없음. 빼거나 `null`이면 비운 것. 서버가 채워 넣지 않는다 | PRD 4절 3번 |
| `mood` | 필수 | 기분 이름 5개 중 하나: 설렘, 행복, 평온, 피곤, 아쉬움 | PRD 4절 3번, D-016 |
| `photo` | 선택 | 0~1장. 빼거나 `null`이면 사진 없음. 1절 "사진 올리기와 보기"의 사진 칸 규칙 | PRD 4절 3번, R-D-017, D-033 |

- 기간 검사에 쓰는 여행은 `POST`는 본문의 `trip_id`, `PUT`은 그 일기에 저장된 `trip_id`의 여행이다.
- `time`을 두 자리로 맞추는 이유: 글자 순서대로 정렬해야 시간 순서가 맞는다 (`09:05`는 되고 `9:05`는 안 된다) (D-016).
- `id`, `created_at`, `updated_at`은 본문에 넣지 않는다 (1절 "주고받는 값").
- 글자 값은 앞뒤 공백을 빼고 저장한다. 글자 수도 뺀 뒤 센다. 선택 항목을 비우거나 공백만 적으면 `null`이다 (D-029).

### 4. API별 규칙

**`GET /api/diaries?trip_id={tripId}` — 여행별 일기 목록**
- 순서: `date`가 오래된 것이 앞, 같으면 `time`이 이른 것, 그것도 같으면 `id`가 작은 것이 앞 (DATA-MODEL 4절 2번). 여행 상세는 이 순서 그대로, 다이어리 화면은 뒤집어 최신순으로 보인다 (R-D-008, D-034).
- 일기가 없으면 `200` + `[]` (D-020).
- `trip_id`를 빼면 `422` (FastAPI 자동).
- 없는 여행의 `trip_id`면 `200` + `[]` (AI 제안. 3절과 같다). 화면은 주소의 여행 번호가 여행 목록에 없으면 "전체 여행"으로 시작하므로 이 API를 부르지 않는다 (SCREEN-SPEC 5절 5번, D-034).
- 페이지를 나누지 않는다. 여행을 고른 화면과 여행 상세가 이 목록 전체를 쓴다 (D-034).

**`GET /api/diaries/page?page={page}&size={size}` — 전체 보기 한 페이지 (D-034)**
- 모든 여행의 일기를 `date`가 늦은 것, 같으면 `time`이 늦은 것, 그것도 같으면 `id`가 큰 것부터 줄 세워 `page`번째 묶음(`size`편)을 돌려준다.
- `page`는 1부터, 빼면 1. `size`는 1~50, 빼면 20. 숫자가 아니거나 범위를 벗어나면 `422` (FastAPI 자동, AI 제안).
- 응답: `{ "items": [일기 객체…], "total": 22 }`. `items`의 일기 객체에는 `trip_name`이 더 붙는다. `total`은 모든 여행의 일기 개수다 (AI 제안. 3절과 같다).
- 마지막 페이지보다 큰 `page`면 `items`는 `[]`이고 `total`은 그대로다 (3절과 같다).
- 일기가 하나도 없으면 `200` + `{ "items": [], "total": 0 }` (D-020).

**`GET /api/diaries/recent` — 최근 일기 1개**
- 모든 여행에서 `date`·`time`이 늦은 것, 같으면 `id`가 큰 것 1개 (R-D-013, H-02, H-05, DATA-MODEL 4절 2번).
- 일기가 하나도 없으면 `200` + `null` (D-020).

**`GET /api/diaries/{id}` — 일기 하나**
- 고치기 폼 화면(`/diary/:id/edit`)이 쓴다. 없는 `id`면 `404` (SCREEN-SPEC 5절 5번 "찾을 수 없는 일기예요").
- 폼에 보일 여행 이름·기간은 응답의 `trip_id`로 `GET /api/trips/{id}`를 불러 얻는다 (2절 5번).

**`POST /api/diaries` — 일기 쓰기**
- 같은 날짜·시각의 일기가 이미 있어도 저장한다 (R-D-002).
- 성공하면 `201`과 만든 일기 객체를 돌려준다. 화면은 `/diary?trip=:tripId` 목록으로 돌아간다 (SCREEN-SPEC 5절 3번).

**`PUT /api/diaries/{id}` — 일기 고치기**
- 검사 순서: 로그인하지 않았으면 `401` → 입력 규칙을 어기면 `422` → 없는 `id`면 `404` → 그 여행의 주인이 아니면 `403` (D-029, D-042).
- 성공하면 라우터가 `updated_at`을 지금 시각으로 바꾸고, `200`과 고친 일기 객체를 돌려준다 (D-017).
- 사진을 바꾸거나 뺐으면 전 사진 파일을 지운다 (1절 "사진 올리기와 보기").

**`DELETE /api/diaries/{id}` — 일기 지우기**
- 로그인하지 않았으면 `401` → 없는 `id`면 `404` → 그 여행의 주인이 아니면 `403` (D-042). 성공하면 사진 파일도 지우고 `204`, 본문 없음 (R-D-010, D-033).

## 5. Home이 쓰는 API (담당: 은희)

> 근거: D-004, PRD 5절, SCREEN-SPEC 6절, ARCHITECTURE 5절. Home은 세 기능의 API를 가져다 쓰기만 한다. Home만을 위한 API와 `frontend/src/api/` 파일은 없다.

### 1. 블록별 API

| 블록 | API | 쓰는 필드 | 비었을 때 | 근거 |
| --- | --- | --- | --- | --- |
| A. 최근 여행 | `GET /api/trips` (2절)의 첫 번째 | `id`, `name`, `destination`, `start_date`, `end_date` | `[]` → 첫 방문 화면 | PRD H-01, R-H-001, R-H-012 |
| B. 최근 장소 | `GET /api/places/recent` (3절) | `name`, `region`, `visit_date` (`rating`은 쓰지 않는다, D-043) | `null` → "아직 넣은 장소가 없어요." | PRD H-01, R-H-002, R-P-013 |
| C. 최근 일기 | `GET /api/diaries/recent` (4절) | `date`, `mood`, `title` (`time`은 쓰지 않는다) | `null` → "아직 쓴 일기가 없어요." | PRD H-01, R-H-003, R-D-013 |
| D. 바로가기 | 없음 | — | — | R-H-006 |

- "최근" 순서는 각 API가 정한다. Home은 받은 것을 그대로 보인다 (H-02, H-05).
  - A: `start_date` 늦은 것, 같으면 `id` 큰 것 (2절 4번)
  - B: `visit_date` 늦은 것, 같으면 `id` 큰 것 (3절 4번)
  - C: `date`·`time` 늦은 것, 같으면 `id` 큰 것 (4절 4번)
- A 카드를 누르면 받은 `id`로 `/trip/:id`에 간다 (R-H-005). B·C 카드는 받은 `trip_id`로 `/place?trip=:tripId`, `/diary?trip=:tripId`에 간다 (2026-10-23 팀 합의).
- C의 기분은 `mood` 이름에 맞는 이모지로 보인다 (D-016, 4절 5번).
- A·B·C 모두 사진은 보이지 않는다. 응답에 사진 칸이 더해져도 Home은 쓰지 않는다 (D-033).

### 2. 부르는 방법

- Home 화면(`frontend/src/pages/Home/`)은 `frontend/src/api/`의 `trips.js` · `places.js` · `diaries.js`에 있는 함수를 부른다 (AGENTS 코드 규칙).
- A·B·C는 따로 부르고 따로 보인다. 한 API가 오류여도 나머지 블록은 그대로 보인다 (SCREEN-SPEC 6절 5번).
- 여행이 하나도 없는지는 A의 결과(`[]`)만 보고 판단한다. 여행이 없으면 장소·일기도 없기 때문이다 (SCREEN-SPEC 6절 5번, R-H-012).

### 3. 알고 있는 한계

- A는 첫 번째 여행 하나만 쓰지만 여행 목록 전체를 받는다. 여행 수가 적은 MVP라 그대로 둔다 (PRD 1절 열린 질문 "서준이 따로 만들 API는 없다").

## 6. `recommend` AI 여행지 추천 (담당: 팀 공동)

> 근거: D-037, PRD 6절, SCREEN-SPEC 7절. 라우터 `backend/routers/recommend.py`, 부르는 곳 `frontend/src/api/recommend.js`.
> 주소, 요청·응답 모양, 상태 코드, 오류 문구, 기다리는 시간은 AI 제안을 2026-10-23 사람이 확정했다 (D-037).

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `POST` | `/api/recommend` | 고른 답으로 AI에게 국내 도시 3곳을 추천받는다 | `200` + 추천 객체 | `422`, `502`, `503` |

- 만드는 것이 없으므로 공통 규칙의 `POST` → `201`(1절 "메서드")이 아니라 `200`을 쓴다.
- DB를 읽지도 쓰지도 않는다.

### 2. 추천 객체 (응답)

```json
{
  "items": [
    {
      "city": "강릉시",
      "region": "강원",
      "reason": "바다를 보며 조용히 쉬기 좋고, 혼자 다니기에도 편한 곳이에요.",
      "activities": ["경포 해변 산책", "바닷가 카페에서 쉬기", "초당 순두부 먹기"]
    }
  ]
}
```

| 필드 | 모양 | 뜻 |
| --- | --- | --- |
| `items` | 목록, 늘 3개 | 추천한 곳. 화면은 이 순서대로 1·2·3번으로 보인다 |
| `city` | 글자 | 도시(시·군) 이름. 예: "강릉시", "경주시". AI가 "시"·"군"을 붙이거나 빼서 보낼 수 있고, 그대로 보인다 (2026-10-23 사람이 정함) |
| `region` | 글자 | 시·도. 장소 기능의 17개 이름(`서울`, `부산`, `대구`, `인천`, `광주`, `대전`, `울산`, `세종`, `경기`, `강원`, `충북`, `충남`, `전북`, `전남`, `경북`, `경남`, `제주`) 중 하나 (3절 `places`와 같은 목록) |
| `reason` | 글자 | 추천 이유 한두 문장 |
| `activities` | 글자 목록, 2~3개 | 그곳에서 할 만한 것 |

- `id`, `created_at`이 없다. 저장하지 않기 때문이다.

### 3. 요청 본문과 서버 검사

```json
{ "mood": "지침", "styles": ["자연", "바다"], "companion": "혼자", "duration": "1박 2일", "note": null }
```

| 필드 | 필수 | 규칙 | 어기면 |
| --- | --- | --- | --- |
| `mood` | 예 | `지침` · `설렘` · `평온` · `심심` · `우울` 중 하나 | `422` |
| `styles` | 예 | `자연` · `바다` · `맛집` · `역사·문화` · `액티비티` · `휴식` 중에서 1개 이상, 겹치지 않게 | `422` |
| `companion` | 예 | `혼자` · `친구` · `연인` · `가족` 중 하나 | `422` |
| `duration` | 예 | `당일` · `1박 2일` · `2박 3일` · `3박 이상` 중 하나 | `422` |
| `note` | 아니오 | 앞뒤 공백을 빼고 100자까지. 비었거나 공백만이면 `null`로 본다 (D-021과 같은 생각) | 100자를 넘으면 `422` |

- 서버도 화면과 같은 규칙을 검사한다 (D-019). 화면이 선택지로만 보내므로 `422`는 드물다.
- 선택지 이름은 화면에 보이는 글자 그대로다. 영어 코드로 바꾸지 않는다.

### 4. API별 규칙

| 경우 | 응답 |
| --- | --- |
| 본문이 3번 규칙을 어김 | `422` (FastAPI 기본 모양, 1절 "오류 응답") |
| 서버에 AI 키(`GEMINI_API_KEY`, D-038)가 없음 | `503`, `{"detail": "AI 키가 설정되지 않았어요"}`. AI를 부르지 않는다 |
| AI를 부르다 실패함 (키가 틀림, 무료 한도를 넘음(Gemini `429`), 네트워크, 두 모델 모두 시간 초과 등) | `502`, `{"detail": "추천을 받지 못했어요"}` |
| AI 응답이 2번 모양이 아님 (3곳이 아님, `region`이 17개 이름 밖, `activities`가 2~3개가 아님 등) | `502`, `{"detail": "추천을 받지 못했어요"}` |
| 그 밖 | `200` + 2번 추천 객체 |

- 검사 순서: 본문 `422` → 키 `503` → AI 호출·응답 `502`.
- 서버는 AI에게 고른 답만 보낸다. 여행·장소·일기 데이터는 보내지 않는다 (PRD 6절 6번).
- AI는 Google Gemini 무료 등급의 `gemini-3.8-flash`이고, 응답을 2번 모양(JSON)으로 받도록 서버가 요청한다 (D-038). 처음에는 Claude Opus 5.5였다 (D-037).
- `gemini-3.8-flash`가 Google 서버 오류(`5xx`: 혼잡 `503`, 시간 초과 `504` 등)를 돌려주면 같은 요청을 `gemini-3.5-flash-lite`로 한 번 더 보낸다. 첫 모델은 20초까지만 기다리고, 넘으면 같은 방식으로 `gemini-3.5-flash-lite`에 보낸다 (D-041). 두 번째 모델은 60초까지 기다린다. 두 번째 모델도 실패하거나 그 밖의 실패(`4xx`, `429`, 응답 모양이 틀림)면 `502`다 (D-039, D-040, D-041). AI에게 보내는 지시문은 `recommend.py` 안에 둔다.
- AI 오류의 자세한 내용(키 값, AI 회사의 오류 글)은 응답에 넣지 않는다. 서버 터미널 로그에만 남긴다. 키 값은 로그에도 남기지 않는다.
- 같은 요청을 보내도 응답은 매번 다를 수 있다.

### 5. 다른 기능이 쓰는 곳

- 추천 대화창(`frontend/src/components/RecommendChat/`, SCREEN-SPEC 7절)만 쓴다. 다른 기능은 쓰지 않는다.
- 화면의 `502`·`503`·서버에 닿지 못함 처리는 SCREEN-SPEC 7절 5번을 따른다. `422`는 `502`와 같은 문구로 보인다.

## 7. `users` 회원 (담당: 팀 공동)

> 근거: D-042, PRD 7절, SCREEN-SPEC 8절, DATA-MODEL 6·7절. 라우터 `backend/routers/users.py`, 부르는 곳 `frontend/src/api/users.js`.
> 주소, 요청·응답 모양, 상태 코드, 문구는 AI 제안이다 (P-70 뒤 사람이 확인).

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `POST` | `/api/users` | 회원가입. 성공하면 바로 로그인된다 | `201` + 회원 객체 + 쿠키 | `422`, `409` |
| `POST` | `/api/users/login` | 로그인 | `200` + 회원 객체 + 쿠키 | `422`, `401` |
| `POST` | `/api/users/logout` | 로그아웃 | `204` + 쿠키 지우기 | — |
| `GET` | `/api/users/me` | 지금 로그인한 회원 | `200` + 회원 객체 또는 `null` | — |

### 2. 회원 객체

```json
{
  "id": 1,
  "login_id": "yeoback_1",
  "nickname": "여행하는 곰",
  "profile_photo": "5d4c3b2a19f8e7d6c5b4a39281706f5e.png",
  "created_at": "2026-10-23 15:00:00",
  "updated_at": "2026-10-23 15:00:00"

```

| 필드 | 뜻 | 비었을 때 | 근거 |
| --- | --- | --- | --- |
| `id` | 회원 번호 | — | DATA-MODEL 6절 |
| `login_id` | 아이디 | — | DATA-MODEL 6절 |
| `nickname` | 닉네임 | — | DATA-MODEL 6절 |
| `profile_photo` | 프로필사진 파일 이름. 화면은 `/api/uploads/{profile_photo}`로 보인다 | `null` | DATA-MODEL 6절, D-033 |
| `created_at`, `updated_at` | 가입·고친 시각 | — | D-020 |

- 비밀번호와 `password_hash`는 어떤 응답에도 넣지 않는다 (D-042).

### 3. 요청 본문과 서버 검사

**`POST /api/users` (가입)**

```json
{ "login_id": "yeoback_1", "password": "abcd1234!", "nickname": "여행하는 곰", "profile_photo": null }
```

| 필드 | 필수 | 서버가 검사하는 규칙 | 근거 |
| --- | --- | --- | --- |
| `login_id` | 필수 | 4~20자, 영문 소문자·숫자·`_`만 (`^[a-z0-9_]{4,20}$`). 앞뒤 공백을 빼지 않는다(공백이 있으면 `422`) | PRD 7절 3번 |
| `password` | 필수 | 8~20자, 공백을 뺀 영문·숫자·기호(ASCII `!`~`~`)만. 그래서 bcrypt의 72바이트 한계를 넘지 않는다 | PRD 7절 3번 |
| `nickname` | 필수 | 앞뒤 공백을 빼고 2~10자. 공백만 적으면 비운 것으로 본다 (D-021) | PRD 7절 3번 |
| `profile_photo` | 선택 | 0~1장. 빼거나 `null`이면 사진 없음. 1절 "사진 올리기와 보기"의 사진 칸 규칙 | D-033, D-042 |

- "비밀번호 확인"은 화면에서만 검사하고 보내지 않는다.

**`POST /api/users/login` (로그인)**

```json
{ "login_id": "yeoback_1", "password": "abcd1234!" }
```

- 두 칸 모두 필수 글자다. 빠지면 `422`. 글자 꼴(4~20자 등)은 검사하지 않고, 맞는 회원이 없거나 비밀번호가 틀리면 똑같이 `401`이다.

**`PUT /api/users/me` (회원정보수정)**

```json
{ "nickname": "바다 곰", "profile_photo": null, "current_password": null, "new_password": null }
```

| 필드 | 필수 | 서버가 검사하는 규칙 |
| --- | --- | --- |
| `nickname` | 필수 | 가입과 같다 |
| `profile_photo` | 선택 | 가입과 같다. `PUT`이라 폼의 값 전체를 보낸다 (D-018). 바꾸거나 빼면 전 사진 파일을 지운다 |
| `current_password` | `new_password`가 있을 때 필수 | 지금 비밀번호. 틀리면 `403` |
| `new_password` | 선택 | 비밀번호를 바꿀 때만 넣는다. 가입의 `password`와 같은 규칙. 빼거나 `null`이면 비밀번호를 바꾸지 않는다 |

- `login_id`는 바꿀 수 없다. 본문에 넣어도 쓰지 않는다.

### 4. API별 규칙

**`POST /api/users` — 회원가입**
- 검사 순서: 본문 `422` → 아이디가 이미 있으면 `409` `{"detail": "이미 쓰는 아이디예요"}`.
- 비밀번호를 bcrypt로 해시해 `password_hash`에 넣는다 (D-042).
- 가입을 저장할 때 같은 트랜잭션에서 `user_id`가 `null`인 여행을 모두 처음 가입한 회원(`id`가 가장 작은 회원)의 것으로 바꾼다. 첫 가입이면 이 회원이다 (DATA-MODEL 1절, D-042).
- 성공하면 세션을 만들고 쿠키를 준다(1절 "로그인"). `201`과 회원 객체를 돌려준다.
- 이미 로그인한 채로 가입해도 막지 않는다. 새 회원으로 로그인된다 (전 세션 줄은 지운다, AI 제안).

**`POST /api/users/login` — 로그인**
- 아이디가 없거나 비밀번호가 틀리면 `401` `{"detail": "아이디 또는 비밀번호가 맞지 않아요"}`. 어느 쪽이 틀렸는지 가르지 않는다.
- 성공하면 세션을 만들고 쿠키를 준다. 이미 로그인한 쿠키가 있으면 그 세션 줄은 지운다 (AI 제안).

**`POST /api/users/logout` — 로그아웃**
- 쿠키의 세션 줄을 지우고 쿠키를 지운다. 로그인하지 않았어도 `204`다.

**`GET /api/users/me` — 지금 로그인한 회원**
- 로그인하지 않았으면 `200` + `null` (D-020의 "없으면 `null`"과 같은 생각). `401`로 돌려주지 않는다. 화면이 "로그인 안 함"과 오류를 가를 수 있게 하기 위해서다.
- 화면은 앱을 열 때 한 번 부르고, 로그인·가입·로그아웃·정보수정 뒤에 다시 부르거나 받은 객체로 바꾼다.

**`PUT /api/users/me` — 회원정보수정**
- 검사 순서: 로그인 `401` → 본문 `422` → 지금 비밀번호가 틀림 `403` `{"detail": "지금 비밀번호가 맞지 않아요"}`.
- 비밀번호를 바꾸면 이 회원의 다른 세션을 모두 지운다. 지금 쿠키의 세션은 남긴다 (DATA-MODEL 7절).
- 성공하면 `updated_at`을 지금 시각으로 바꾸고 `200`과 고친 회원 객체를 돌려준다 (D-017).

### 5. 다른 기능이 쓰는 곳

| 쓰는 곳 | API | 쓰는 것 |
| --- | --- | --- |
| 공통 레이아웃 네비 (건용) | `GET /api/users/me` | 로그인 여부, `nickname`, `profile_photo` |
| 여행·장소·다이어리 화면 (버튼 보이기) | `GET /api/users/me` | `id`를 여행의 `user_id`와 견준다 |
| 여행 상세의 좋아요·댓글 | `GET /api/users/me` | 로그인 여부, `id`(내 댓글인지) |

- 화면이 로그인한 회원을 어떻게 여러 화면에 나눠 주는지(공통 상태)는 `ARCHITECTURE` 5절에 적는다.

### 6. 다른 문서로 넘길 것

| 내용 | 문서 |
| --- | --- |
| 가입·로그인·로그아웃·정보수정, `401`·`403`·`409`, 쿠키가 생기고 지워지는지, 응답에 비밀번호가 없는지, 첫 가입자에게 여행이 붙는지 검사 | `TEST-PLAN` 9절 |
| `bcrypt` 패키지 | `ARCHITECTURE` 2절 |

### 7. 열린 질문

- 이 절의 주소·모양·문구는 AI 제안이다. 글자 규칙은 PRD M-01을 따른다.

## 8. `likes` 여행 좋아요 (담당: 팀 공동)

> 근거: D-042, PRD 7절 R-M-009, DATA-MODEL 8절. 라우터 `backend/routers/likes.py`, 부르는 곳 `frontend/src/api/likes.js`. 주소·모양은 AI 제안이다.

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `POST` | `/api/likes` | 좋아요 누르기 | `200` + 좋아요 상태 | `401`, `422` |
| `DELETE` | `/api/likes?trip_id={tripId}` | 좋아요 취소 | `200` + 좋아요 상태 | `401`, `422` |

- 공통 규칙(`POST` → `201`, `DELETE` → `204`, 1절 "메서드")과 다르다. 이미 누른 것을 또 눌러도 오류 없이 같은 결과를 주고, 화면이 바뀐 개수를 바로 보일 수 있게 둘 다 `200`과 좋아요 상태를 돌려준다 (AI 제안).
- 좋아요 수와 내가 눌렀는지는 여행 객체(2절)에도 있다. 좋아요만 따로 가져오는 `GET`은 두지 않는다.

### 2. 좋아요 상태 (응답)

```json
{ "trip_id": 1, "like_count": 4, "liked": true }
```

| 필드 | 뜻 |
| --- | --- |
| `trip_id` | 여행 번호 |
| `like_count` | 그 여행의 지금 좋아요 수 |
| `liked` | 지금 로그인한 회원이 눌렀는지 (누르기 뒤 `true`, 취소 뒤 `false`) |

### 3. 요청 본문과 서버 검사

- `POST` 본문: `{ "trip_id": 1 }`. `trip_id`는 있는 여행의 `id`. 빠지거나 없는 여행이면 `422` (1절 "오류 응답"의 본문 `trip_id` 규칙).
- `DELETE`는 본문 없이 주소에 `trip_id`를 넣는다. 빠지거나 없는 여행이면 `422` (`POST`와 맞춘다, AI 제안).

### 4. API별 규칙

- 검사 순서: 로그인 `401` → `trip_id` `422`.
- `POST`: 이미 눌렀으면 줄을 더하지 않고 지금 상태를 돌려준다 (`UNIQUE (trip_id, user_id)`, DATA-MODEL 8절).
- `DELETE`: 누르지 않았으면 지우지 않고 지금 상태를 돌려준다.
- 내 여행에도 누를 수 있다. 주인이 없는 여행에도 누를 수 있다.

### 5. 다른 기능이 쓰는 곳

- 여행 상세의 좋아요 버튼(서준 화면, SCREEN-SPEC 8절)만 부른다. 여행 목록 카드는 여행 객체의 `like_count`만 보인다.

### 6. 다른 문서로 넘길 것

| 내용 | 문서 |
| --- | --- |
| 누르기·두 번 누르기·취소·`401`·`422`, 여행 객체의 `like_count`·`liked`가 맞는지 검사 | `TEST-PLAN` 9절 |

### 7. 열린 질문

지금은 없다.

## 9. `comments` 여행 댓글 (담당: 팀 공동)

> 근거: D-042, PRD 7절 R-M-010·R-M-011, DATA-MODEL 9절. 라우터 `backend/routers/comments.py`, 부르는 곳 `frontend/src/api/comments.js`. 주소·모양은 AI 제안이다.

### 1. API 목록

| 메서드 | 주소 | 하는 일 | 성공 | 오류 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/comments?trip_id={tripId}` | 여행별 댓글 목록 | `200` + 댓글 객체 목록 | `422` |
| `POST` | `/api/comments` | 댓글 쓰기 | `201` + 만든 댓글 객체 | `401`, `422` |
| `DELETE` | `/api/comments/{id}` | 댓글 지우기 | `204` | `401`, `404`, `403` |

- 댓글 고치기(`PUT`)는 없다 (D-042).

### 2. 댓글 객체

```json
{
  "id": 7,
  "trip_id": 1,
  "user_id": 2,
  "nickname": "바다 곰",
  "profile_photo": null,
  "content": "사진이 정말 좋아요!",
  "created_at": "2026-10-23 16:20:00",
  "updated_at": "2026-10-23 16:20:00"
}
```

| 필드 | 뜻 | 비었을 때 |
| --- | --- | --- |
| `id`, `trip_id`, `user_id` | 댓글·여행·쓴 회원 번호 | — |
| `nickname`, `profile_photo` | 쓴 회원의 지금 닉네임·프로필사진 (`users`에서 붙여 넣음) | `profile_photo`는 `null` |
| `content` | 댓글 내용 (줄바꿈 그대로) | — |
| `created_at`, `updated_at` | 쓴 시각. 화면은 `created_at`을 보인다 | — |

### 3. 요청 본문과 서버 검사

- `POST` 본문: `{ "trip_id": 1, "content": "사진이 정말 좋아요!" }`
- `trip_id`: 있는 여행의 `id`. 빠지거나 없는 여행이면 `422`.
- `content`: 앞뒤 공백을 빼고 1~200자. 비거나 공백만이면 `422` (D-021, D-029).

### 4. API별 규칙

**`GET /api/comments?trip_id={tripId}`**
- 순서: `id`가 작은 것(먼저 쓴 것)이 앞 (DATA-MODEL 9절).
- 로그인 없이 부른다. 댓글이 없거나 없는 여행이면 `200` + `[]` (3절 장소 목록과 같다). `trip_id`를 빼면 `422`.

**`POST /api/comments`**
- 검사 순서: 로그인 `401` → 본문 `422`. 주인이 아니어도, 주인이 없는 여행에도 쓸 수 있다.
- 성공하면 `201`과 만든 댓글 객체.

**`DELETE /api/comments/{id}`**
- 검사 순서: 로그인 `401` → 없는 `id` `404` `{"detail": "댓글을 찾을 수 없어요"}` → 쓴 회원이 아니면 `403` `{"detail": "내 댓글만 지울 수 있어요"}`. 여행 주인도 남의 댓글을 지우지 못한다.
- 성공하면 `204`, 본문 없음.

### 5. 다른 기능이 쓰는 곳

- 여행 상세의 댓글 칸(서준 화면, SCREEN-SPEC 8절)만 부른다. 상세의 댓글 수("댓글 N")는 이 목록의 길이로 센다. 여행 목록 카드의 댓글 수는 여행 객체의 `comment_count`를 쓴다 (2절, D-045).

### 6. 다른 문서로 넘길 것

| 내용 | 문서 |
| --- | --- |
| 목록 순서, 쓰기·지우기, `401`·`403`·`404`·`422`, 여행을 지우면 댓글도 사라지는지 검사 | `TEST-PLAN` 9절 |

### 7. 열린 질문

- 200자는 AI 제안이다 (PRD M-01).
